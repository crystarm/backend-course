# Популярные ошибки 1 лабораторной

## Папка .idea в репозитории

Папка .idea предназначена для хранения конфигураций и индексов IDE для проекта. 
То есть когда вы создаете/клонируете репозиторий, ваша среда разработки анализирует код, и чтобы каждый раз не пересчитывать, складирует
накопленные знания о вашем проекте в папку .idea.
Во многом эта папка носит личный характер и сильно зависима от вашей операционной системы, версии и настроек idea. 
Очевидно, что другому разработчику она не нужна, поскольку его среда разработки должна самостоятельно все проанализировать.
Более того, она сильно мешает и вызывает конфликты. 

По умолчанию, при создании проекта, папка .idea добавляется в git. 
Очень важно прописать ее в .gitignore файл целиком, например так:
```gitignore
.idea
```
Проконтролируйте, что в репозиторий папка .idea никак не попала. Если вдруг такое случилось — явно удалите ее.

## Папка target в репозитории

Папка target содержит файлы, созданные во время сборки проекта, такие как классы, jar-файлы и другие ресурсы. 
Эти файлы не должны попадать в репозиторий, поскольку они могут быть громоздкими и не нужны для работы других разработчиков.

## Использование группы "com.karandashov"

Пожалуйста, будьте внимательны при копировании из туториалов. GroupId "com.karandashov" используется в лабораторных для примеров,
не нужно использовать его в своих проектах. Вместо этого выберите уникальный groupId, например, основанный на вашем домене или имени.

## Вся логика написана в Main

Пожалуйста, не пишите всю логику в классе Main. 
Разбейте логику на отдельные классы, чтобы каждый отвечал за свою функциональность.

## Классы не разложены по пакетам

Пожалуйста, разделяйте классы по пакетам. Это улучшает структуру кода и делает его более читаемым и поддерживаемым.

## Ошибки многомодульности проекта

Главная цель, почему мы используем многомодульный репозиторий, — это унификация содержимого. 
Основная идея в том, что все модули должны быть максимально похожи друг на друга с точки зрения используемых библиотек и плагинов.

Представьте, что в вашем репозитории находится несколько полностью отдельных сервисов. Один использует junit 5 для написания тестов, 
второй уже переехал на junit 6. Это влечет за собой невозможность переиспользования и трудности при поддержке. 

Именно поэтому мы располагаем в корне репозитория корневой файл pom.xml, главная задача которого определить версии используемых
jdk/библиотек/плагинов. 
Посмотрите, как устроен [корневой pom.xml данного репозитория](../../pom.xml). Он содержит блоки:
* properties — версии jdk/библиотек/плагинов в формате ключ-значение
* modules — **обязательно укажите** папки, в которых нужно искать подмодули
* dependencyManagement — описание версий всех используемых библиотек с отсылкой на properties
* build.pluginManagement — общие для сервисов плагины сборки (например maven-surefire-plugin для прогона тестов)

В корне вашего проекта должен лежать очень похожий pom.xml, главное не забывайте менять groupId на свой собственный.
Видеть в лабораторных <groupId>com.karandashov</groupId> как-то не очень.

В свою очередь pom.xml вашего проекта должен выглядеть [примерно так](../../jbcd-1-core/jbcd-1a-first-program/pom.xml), то есть
состоять из блоков:
* parent — **обязательный блок**, который ссылается на корневой pom.xml и говорит maven пользоваться объявленными там правилами
* dependencies — конкретные, используемые именно в этом модуле библиотеки (без указания версий, мы указали их в корневом)
* build.plugins — настройки сборки именно этого модуля (например используется особенный main класс или пакет, или требуется fat jar)

То есть в pom.xml конкретного модуля уже точно не нужны properties! Не дублируйте.
