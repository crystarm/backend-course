# Задания курса

## Правила оформления кода, принятые на курсе

1. Имя проекта/сервиса пишется через дефис маленькими буквами в kebab-case.
2. Имена классов именуются с большой буквы в CamelCase.
3. Имена переменных, полей классов, параметров методов и самих методов пишутся с маленькой буквы в lowerCamelCase.
4. Имена констант пишутся большими буквами в SCREAMING_SNAKE_CASE.
5. Названия должны нести смысловую нагрузку и желательно не сокращаться (кроме общепринятых сокращений типа Impl, Config, App).
6. Имя класса/поля/переменной/метода должны соответствовать содержимому. Например, не стоит даже временно класть значение счетчика в переменную, обозначающую возраст.
7. Если класс принадлежит к определенному слою (Service, Dao, Transformer, Dto), то это нужно отразить в его названии (но не используйте в названии класса слова Model/Domain/Data/Object).
8. Интерфейсам нужно давать "нормальное" имя без приставок, показывающих принадлежность к интерфейсам, а к имени реализации добавлять или (лучше) добавить в название особенности реализации (например, PersonDaoJdbc для интерфейса PersonDao).
9. Классы должны лежать в пакетах. Главный класс, точка входа в приложение, лежит в корневом пакете ("ru.ivanov"), а все остальные классы должны лежать в подпакетах ("ru.ivanov.service").
10. Все поля классов должны быть приватными и быть доступными только через методы (геттеры и сеттеры).
11. Константы должны быть static final. Без static это не константы.
12. Код должен быть отформатирован так же, как это бы произошло при нажатии сочетания клавиш Alt + Ctrl + L в IDEA (⌥⌘L в macOS).
13. Желательно всегда писать блок {} для if-а и for-а. Исключением является, если тело if содержит return.
14. Если несколько строк кода выполняют законченное действие, то они должны быть вынесены в метод.
15. Если один или несколько методов не относятся напрямую к логике класса, то они должны быть вынесены в отдельный класс (например, сервис).

## Лабораторные работы

2) [database](2-database)

Для сдачи лабораторных работ вам потребуется публичный репозиторий на GitHub или GitLab.
Все 3 лабораторные работы необходимо выполнить в нем. Используйте Maven как систему сборки.
**Отчеты писать не требуется: мне интересен код, а не бессмысленная писанина.**

Соблюдайте порядок действий:
* внимательно проверить свой вариант по актуальному списку группы
* выполнить N-ую работу, залить в репозиторий 
* прикрепить ссылку на репозиторий в гугл класс к соответствующему заданию (кнопка "+ Добавить или создать" → "Ссылка")
* * архивы проверяться не будут!
* * ссылку нужно прикрепить именно в задание, а не писать комментарием!
* нажать кнопку сдать
* прийти на ближайшую очную защиту (желательно взять ноутбук для демонстрации)
* * нет сданного задания в гугл классе — нет защиты!

## Проектная/курсовая работа

Проект — это возможность применить знания курса в условиях, приближённых к реальной разработке.
Проект выполняется в отдельном репозитории(-ях).

### Требования к проекту

1. **теоретическая** полезность

Ваше приложение должно быть **в теории** кому-то нужно. **Требования к актуальности и уникальности НЕ предъявляются.**
Приложение должно иметь законченный вид и корректно выполнять заявленную функциональность.
Выбор темы и необходимого функционала согласуется с преподавателем.

2. web + бд

По плану минимум, необходимо сделать web-приложение, использующее для хранения базу данных.
Но конечно, приветствуется усложнения и использование и других технологий, рассматриваемых на курсе.

3. от 2 сервисов

Приложение должно состоять хотя бы из 2-х сервисов, взаимодействующих между собой (синхронно и/или асинхронно).

4. Состав команд

Проект выполняется в одиночку или в команде из 2-х человек.
В случае 2 студентов — для приложения становится обязательным web ui.
**Разрешается согласовать с преподавателем большее количество участников, если проект будет достаточно интересным.**
Все участники должны внести посильный вклад в реализацию проекта.

Работа в обязательном порядке ведется в git-репозитории.
Запрещено:
- использовать squash коммитов
- рассказывать сказки про "обмен zip архивами между участниками команды"
- рассказывать сказки про "работу из-под одной учетки"

5. итоговый результат = репозиторий + защита с презентацией

### Согласование темы

Первым шагом следует согласовать техническое задание с преподавателем. 
ТЗ выполняется в свободной форме и прикрепляется в виде **краткого текстового файла**.
ТЗ обязательно должно содержать:
* Краткое описание приложения
* Основную функциональность
* Состав участников

Срок согласования ТЗ — первая половина семестра. Обратите внимание, что "сдать" != "согласовать". Прикрепляйте ТЗ заранее!
Не генерируйте чушь, нет смысла в 3 листа текста и выдумывании мифической нужности проекта (мы учимся, а не питчим стартапы). 
Попробуйте уложиться в 1 страницу, написанную человеком.

Проект — простор для творчества, попробуйте сделать что-то интересное.

**Примеры** возможных тем:
* платформа для проведения аукционов
* симулятор крипто-биржы
* магазин <чего-либо>
* приложение для отслеживания здоровья/аптечки
* система электронного документооборота
* приложение-помощник студента
* онлайн школа
* сокращатель ссылок + статистика обращений
* продвинутый агрегатор новостей
* CRM для скорой помощи с интеграцией карт
     
Только не надо делать просто tg-бота, пожалуйста. Он может быть вспомогательным, но не основным. 

### Правила оценивания

* 5 баллов — согласование ТЗ в срок
* до 35 баллов — сам проект и дополнения:
* * размещение на сервере на домене
* * ci/cd
* * наличие тестов
* * использование kafka/redis/s3/temporal
* * контейнеризация
* * observability
* * внешние интеграции (tg, email, открытые api, парсинг чего-либо и тд)
* * хорошая реализация регистрации и входа
* * применение паттернов отказоустойчивости
* * качественная защита

Итого вы сможете получить до 40 баллов.

### Курсовая работа

Возможно, вы учитесь в группе, для которой предусмотрена курсовая работа по предмету. 
В этом случае, помимо самого проекта и презентации, необходимо будет подготовить официальный отчет (простите, таковы требования института).

Отчет выполняется в стандартных требованиях к оформлению: times new roman, 14 кегль, выравнивание по ширине.

Отразите в отчете:
* описание приложения
* основную функциональность
* четкое разделение ролей между участниками (если выполняли двое и больше)
* архитектура проекта (нарисуйте в diagram.net)
* интересные технические решения (пробегитесь по правилам оценивания выше)
