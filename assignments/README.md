## Правила оформления кода, принятые на курсе

1. Имя проекта/сервиса пишется через дефис маленькими буквами в kebab-case.
2. Имена классов именуются с большой буквы в CamelCase.
3. Имена переменных, полей классов, параметров методов и самих методов пишутся с маленькой буквы в lowerCamelCase. В java не принято использовать сокращения в названиях переменных, то есть переменная senderUserPaymentInfo — вполне нормальная. Не нужно сокращать до sendUsPayInf — это плохо читается.
4. Имена констант пишутся большими буквами в SCREAMING_SNAKE_CASE.
5. Названия должны нести смысловую нагрузку и желательно не сокращаться (кроме общепринятых сокращений типа Impl, Config, App).
6. Имя класса/поля/переменной/метода должны соответствовать содержимому. Например, не стоит даже временно класть значение счетчика в переменную, обозначающую возраст.
7. Если класс принадлежит к определенному слою (Service, Dao, Transformer, Dto), то это нужно отразить в его названии (но не используйте в названии класса слова Model/Domain/Data/Object).
8. Интерфейсам нужно давать "нормальное" имя без приставок, показывающих принадлежность к интерфейсам, а к имени реализации добавлять или (лучше) добавить в название особенности реализации (например, PersonDaoJdbc для интерфейса PersonDao).
9. Классы должны лежать в пакетах. Главный класс, точка входа в приложение, лежит в корневом пакете ("ru.ivanov"), а все остальные классы должны лежать в подпакетах ("ru.ivanov.service").
10. Все поля классов должны быть приватными и быть доступными только через методы (геттеры и сеттеры).
11. Константы должны быть static final. Без static это не константы.
12. Код должен быть отформатирован так же, как это бы произошло при нажатии сочетания клавиш Alt + Ctrl + L в IDEA (⌥⌘L в macOS).
13. Желательно всегда писать блок {} для if-а и for-а. Исключением является, если тело if содержит return.
14. Если несколько строк кода выполняют законченное действие, то они должны быть вынесены в метод.
15. Если один или несколько методов не относятся напрямую к логике класса, то они должны быть вынесены в отдельный класс (например, сервис).

## Проектная/курсовая работа

Проект — это возможность применить знания курса в условиях, приближённых к реальной разработке.
Проект выполняется в отдельном репозитории(-ях).

### Требования к проекту

0. Основной backend на Java/Kotlin

Основная часть backend'а проекта должна быть на Java/Kotlin.
В качестве системы сборки можно использовать не только Maven, но и Gradle.
Библиотеки/фреймворки никак не ограничены. 

Разумеется это не касается frontend, различных скриптов развертывания, автотестов и тд. Для служебных целей можно все что угодно.

Какие-то специфические части backend'а вполне могут быть не на java. Например, если вы делаете сервис конвертер видео,
то реализовывать сам конвертер на Java будет больновато. Гораздо проще и логичнее будет взять условный ffmpeg. 
Или допустим какой-то сложный расчет матриц, вполне можно реализовать такой сервис на C++/Rust по благо скорости.
Но основная часть backend'а при этом все равно должна быть на Java/Kotlin.

1. **теоретическая** полезность

Ваше приложение должно быть **в теории** кому-то нужно. **Требования к актуальности и уникальности НЕ предъявляются.**
Мы не питчим стартапы, мы учимся.
Приложение должно иметь законченный вид и корректно выполнять заявленную функциональность.
Выбор темы и необходимого функционала согласуется с преподавателем.

Еще раз, для тех, кто не умеет читать: **мне не нужно обосновывать актуальность и нужность вашего проекта!**
Проект может повторять какое-то существующее приложение, никаких проблем.
Это требование формально отсекает проекты по типу "программа рисует два треугольника и квадрат, зачем не знаю".

2. web + бд

По плану минимум, необходимо сделать web-приложение, использующее для хранения базу данных.
Но конечно, приветствуется усложнения и использование и других технологий, рассматриваемых на курсе.

3. от 2 сервисов

Приложение должно состоять хотя бы из 2-х сервисов, взаимодействующих между собой (синхронно и/или асинхронно).

4. Состав команд

Проект выполняется в одиночку или в команде.
В случае командной работы — для приложения становится обязательным какой-то web ui (хотя бы простенький html+css).
**Обязательно согласуйте с преподавателем тему и разделение ответственности**, нельзя делать впятером один CRUD сервис. 
Все участники должны внести посильный вклад в реализацию проекта.

Работа в обязательном порядке ведется в git-репозитории.
Запрещено:
- использовать squash коммитов
- заливать работу одним финальным коммитом (или несколькими в течение пары дней)
- рассказывать сказки про "обмен zip архивами между участниками команды"
- рассказывать сказки про "работу из-под одной учетки"
- рассказывать сказки про учебу на программиста без компьютера

Сразу отвечу на популярные вопросы:

"Можно ли одного человека полностью выделить под devops?" — да, если это будет нормально настроенный ci/cd: сборка образов
с помощью GitLab CI / GitHub Actions / Jenkins + деплой в небольшой kubernetes (aka k3s на vps) с помощью argo cd +
observability + SSO при необходимости.
Если вы действительно DevOps специалист, ~~а не просто халтурите~~, то для вас это не будет проблемой.
Просто сделать gitlab ci файлик и задеплоить с помощью bash-скрипта на сервер с docker compose — не тянет на полноценного выделенного члена команды,
ему придется делать что-то еще. На курсе мы обязательно рассмотрим простой ci, использование docker и деплой на сервере с доменом, не переживайте.

"Можно ли одного человека полностью выделить под frontend?" — только на половину рабочего времени и только если это полноценный нормальный web ui,
например SPA на React/Vue. Если вы действительно Frontend специалист, ~~а не просто халтурите~~, то для вас это не будет проблемой.
На всякий случай подчеркиваю, что у нас курс по backend разработке. Frontend составляющая здесь исключительно вспомогательная.
Меня абсолютно устроит очень простой frontend на минимальном html/css/js, например [как здесь](../jbcd-7-advanced/jbcd-7a-session-auth/src/main/resources/static).
Еще раз: просто накидать html в ресурсы back-приложения — в эпоху нейросетей не считается за frontend.
Frontend'ом считается только полнофункциональный web и/или как вариант Android/Desktop-приложение, но даже в этом случае вы должны будете сделать немного backend.

"Менеджер (в том числе релиз-менеджер, проектный-менеджер, операционный-менеджер, scrum-менеджер и любые другие <>-менеджеры), 
бизнес-аналитик, руководитель, дизайнер, тестировщик" — сразу нет. 
**Перестаньте пытаться обойти предмет! Не прокатит.**
Мы не занимаемся разработкой стартапа, мы учимся!
Даже такие полезные роли как системный-аналитик и архитектор — не нужны для учебного проекта.

**Каждый репозиторий будет исследован ПО КОММИТАМ, вклад каждого участника оценивается отдельно!**

5. итоговый результат = репозиторий + README

Нет никакого желания читать душные сгенерированные бессмысленные отчеты на 50 страниц.
Просто напишите в README:
* описание приложения
* основную функциональность
* четкое разделение ролей между участниками (если выполняли двое и больше)

Попробуйте уложиться в 2 страницы, написанные человеком.
