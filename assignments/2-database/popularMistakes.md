# Популярные ошибки 2 лабораторной

## Ошибки многомодульности проекта

Главная цель, почему мы используем многомодульный репозиторий, — это унификация содержимого.
Основная идея в том, что все модули должны быть максимально похожи друг на друга с точки зрения используемых библиотек и плагинов.

Представьте, что в вашем репозитории находится несколько полностью отдельных сервисов. Один использует junit 5 для написания тестов,
второй уже переехал на junit 6. Это влечет за собой невозможность переиспользования и трудности при поддержке.

Именно поэтому мы располагаем в корне репозитория корневой файл pom.xml, главная задача которого определить версии используемых
jdk/библиотек/плагинов.
Посмотрите, как устроен [корневой pom.xml данного репозитория](../../pom.xml). В корне вашего проекта должен лежать очень похожий pom.xml.
Он содержит блоки:
* properties — версии jdk/библиотек/плагинов в формате ключ-значение
* modules — **обязательно укажите** папки, в которых нужно искать подмодули
* dependencyManagement — описание версий всех используемых библиотек с отсылкой на properties
* build.pluginManagement — общие для сервисов плагины сборки (например maven-surefire-plugin для прогона тестов)

В свою очередь pom.xml вашего проекта должен выглядеть [примерно так](../../jbcd-1-core/jbcd-1a-first-program/pom.xml), то есть
состоять из блоков:
* parent — **обязательный блок**, который ссылается на корневой pom.xml и говорит maven пользоваться объявленными там правилами
* dependencies — конкретные, используемые именно в этом модуле библиотеки (без указания версий, мы указали их в корневом)
* build.plugins — настройки сборки именно этого модуля (например используется особенный main класс или пакет, или требуется fat jar)

То есть в pom.xml конкретного модуля уже точно не нужны properties! Не дублируйте.

## try-with-resources для работы с JDBC

try-with-resources — это конструкция в Java, которая автоматически закрывает ресурсы после использования блока кода.
Она особенно полезна при работе с JDBC, где необходимо закрывать соединения с базой данных, чтобы не привести к утечкам ресурсов.

```java
try (
    Connection conn = connectionFactory.getConnection();
    PreparedStatement ps = conn.prepareStatement(sql);
    ResultSet rs = ps.executeQuery()
) {
    // работа с БД
} catch (SQLException e) {
    // обработка ошибки
}
```

Не колхозьте свой блок finally для закрытия ресурсов!

## При использовании liquibase: сваливание всех changeset в один файл

Посмотрите, как устроен пример [jbcd-3b-tools](../../jbcd-3-database/jbcd-3b-tools).
В ресурсах лежит файл [db.changelog-master.xml](../../jbcd-3-database/jbcd-3b-tools/src/main/resources/db/changelog/db.changelog-master.xml)
который является master-файлом и подключает все остальные изменения в отдельных файлах.
Это позволяет легко поддерживать и расширять базу данных, не переписывая все изменения в одном месте.

## Хардкод параметров подключения к БД

Параметры БД: url, user, password, schema и др — не должны быть жестко записаны в код.
Вынесите их в конфиг или хотя бы в env-переменные.
